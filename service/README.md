# service — продуктовый слой

Русский веб-сервис поверх `cardiag`: запись звука из браузера, согласование
голов модели, разбор от ИИ-механика и сбор корпуса для дообучения.

Каталог отделён от `src/cardiag`, и ни один файл апстрима отсюда не правится —
обновления подтягиваются без конфликтов.

## Запуск

```
cp service/.env.example .env      # заполнить AIMLAPI_KEY
uvicorn service.app:app --port 8080
```

Нужен `ffmpeg` в PATH: браузер отдаёт webm/opus, модель ждёт WAV 48 кГц моно.

## Как устроен ответ

Две фазы, потому что они сильно расходятся по времени.

**Фаза 1 — акустика, около 2 секунд.** `POST /api/analyse` возвращает вердикт,
зону и что делать. Этого достаточно, чтобы показать результат.

**Фаза 2 — механик, около 12 секунд.** `POST /api/mechanic` с `rec_id`
возвращает разбор. Фронт подгружает его отдельно: держать готовый вердикт ради
LLM значит терять пользователя на спиннере.

Модели грузятся один раз при старте, плюс прогрев CLAP эталонным клипом.
Без прогрева первый запрос после деплоя стоил 10.9 секунды вместо 2.2 —
`Classifier.load()` поднимает только линейные головы, а CLAP подтягивается
лениво.

## Почему сырые числа модели не показываются

**Головы не согласованы.** `region` и `cause` обучались раздельно и выдают
несовместимые пары: на `demo.wav` из репозитория это зона «подвеска/рулевое»
вместе с деталью «выхлоп». `labels_ru.zones_agree()` проверяет совместимость,
и при расхождении сервис называет только зону.

**`cause` и `region` не откалиброваны.** В `best_model_clap.joblib` их
температуры равны 1.0 — шкалирование не применялось. Их «0.98» это сырой
softmax. Откалиброваны только `kind` (3.081), `knock` (1.726) и модель триажа,
поэтому заголовок строится на триаже, а проценты по узлам лежат в `debug`.

Промпт механика отдельно запрещает пересказывать эти числа: без запрета модель
цитировала их владельцу, обнуляя всю работу по честной подаче.

## Разбор механиком

Модель выбрана замером на подтверждённом случае (Lada Granta 150 тыс. км,
цокот ГРМ; сервис независимо подтвердил проблему с клапанами). Сравнивались
`gpt-5-1`, `qwen3.7-plus`, `claude-haiku-latest` и `qwen3.5-flash`.

`claude-haiku-latest` дал валидный JSON, верно объяснил связь симптома с
давлением масла, поставил дешёвую проверку раньше дорогой и честно обозначил
пределы вывода. `qwen3.7-plus` показал сопоставимое качество вчетверо дешевле и
доступен через `AIMLAPI_MODEL`. `qwen3.5-flash` выдавал размышления вместо JSON.

Наружу уходят только числа акустической модели, марка, пробег и описание
симптома. **Само аудио остаётся на сервере.** Omni-модели, способные слушать
запись, требуют публичный URL файла — для пользовательских записей это
неприемлемо по 152-ФЗ, поэтому такой путь отклонён.

На вердикте `uncertain` вызов не делается: рассуждать не о чем, модель начнёт
выдумывать, а токены оплачиваются.

## Что известно про точность

Вокабуляр снят с модели, а не из документации: **21** класс `cause` и 6
`region`, тогда как `MODEL_CARD.md` говорит про 12. `bad_wheal_bearing` и
`wheel_bearing` — один узел, разбитый опечаткой; обе метки ведут на одну
карточку. Тест проверяет, что каждый класс переведён, иначе переобученная
модель молча покажет владельцу английский label.

Проверено на одной машине с подтверждённым диагнозом: зона `engine` и деталь
`valvetrain`, диагноз держится на каждом 8-секундном окне и воспроизводится
побайтово. Это устойчивый сигнал, но одного случая мало — для оценки точности и
собирается корпус.

## Известные ограничения

Модель не умеет отвечать «это не автомобиль»: на синтетическом тоне 220 Гц она
выдаёт «fault, ходовая часть». Согласование голов не даёт назвать деталь, но
заголовок всё равно неверен. Нужен guard на чужеродный звук.

Записи в движении непригодны — шум дороги перебивает дефект, и сервис честно
скатывается в `uncertain`.

## Сбор корпуса

```
corpus/
  audio/<id>.wav
  records.jsonl     одна строка на анализ
  feedback.jsonl    что реально нашли в сервисе
  memory.db         SQLite: справки о машинах + подтверждённые исправления
```

`consent_training` хранится вместе с записью: без явного согласия аудио нельзя
использовать для дообучения. `GET /api/stats` показывает, сколько собрано,
сколько раз вердикт совпал с реальностью и что творится в `memory.db` —
единственная честная метрика качества в проде.

## Память: справки и обучение на фидбеке

`service/memory_store.py` — SQLite-файл в `corpus/`, том же смонтированном
томе, что уже переживает пересборку образа. Ноль новых зависимостей, ноль
новой инфраструктуры. Две таблицы:

**`vehicle_facts`** — второй уровень кэша под справочником из Sonar Pro. Раньше
справки жили только в process-local словаре и обнулялись на каждом редеплое;
теперь `vehicle_facts.lookup_persistent()` проверяет диск между процессом и
сетью: process-dict (микросекунды) → SQLite (диск, переживает редеплой) →
Sonar Pro (сеть, деньги).

**`corrections`** — то, ради чего это всё затевалось. Когда владелец
подтверждает через `/api/feedback`, что реально нашли в сервисе, свободный
текст («направляющие клапанов») размечается фоном (`service/label_mapper.py`,
дешёвая LLM-классификация, `LABEL_MAPPER_MODEL`, по умолчанию
`openai/gpt-4o-mini`) одним из 21 канонического класса `cause` — того же
вокабуляра, что в `labels_ru.PARTS`. Проверено вживую: «направляющие клапанов»
классификатор сам, без подсказки, отнёс к `valvetrain` — той же корзине, куда
я вручную положил направляющие в `labels_ru.py`, потому что отдельного класса
для них в таксономии модели нет.

Дальше `service/export_training_set.py` собирает подтверждённые+размеченные
записи (с согласием на обучение) в папки по классам и вызывает
`cardiag.pipeline.build.ingest_dir()` — тот же путь, которым апстрим принимает
`cardiag ingest --cause <класс>` для "bring your own audio". Никакого нового
формата экспорта: то, что уже понимает `cardiag train`.

```
uv run python -m service.export_training_set
cardiag train
python -m cardiag.training.eval.scorecard   # сверить, что не просело
```

Скрипт предупреждает, но не останавливается, если данных меньше 150 —
переобучение на таком объёме скорее подгонится под шум, чем станет точнее.
Классы с менее чем 5 примерами пропускаются молча. Ни один шаг не запускает
`cardiag train` сам — переобучение не должно быть побочным эффектом экспорта.

**Почему не Memora.** Рассматривался MCP-сервер `memora-mcp` как замена этому
слою. Проверка живым сабпроцессом показала: `memory_absorb`/`memory_digest` —
ровно то, что даёт отслеживание противоречий — в устанавливаемой с PyPI версии
(0.2.22) не зарегистрированы вообще, а `memory_create` подвисал на 15+ секунд
без вины сети. Без `absorb` Memora сводится к сетевому key-value хранилищу
поверх той же справки — то есть строго хуже локальной SQLite для этой задачи,
и добавляет сетевую зависимость на путь, который обязан быть быстрым.

## Прод

```
cp service/.env.example .env      # AIMLAPI_KEY и DOMAIN
docker compose up -d
```

`docker-compose.yml` поднимает сервис за Caddy, который сам получает TLS.
**HTTPS обязателен**: браузер не даёт доступ к микрофону на любом хосте кроме
localhost без защищённого соединения, то есть без сертификата главная функция
не работает.

Образ прогревает CLAP на сборке — иначе каждый деплой тянет 2 ГБ с
HuggingFace, а этот канал из России нестабилен.

Один воркер держит модель в памяти (~700 МБ). Масштабироваться репликами за
прокси, а не воркерами.

Перед публичным запуском:

- Ключ AIMLAPI держать только в `.env`. Файл в `.gitignore`; форк публичный.
- `corpus/` перевести на S3, `records.jsonl` — в PostgreSQL.
- Хостинг в РФ: персональные данные не должны уезжать за границу.
- `_pending` и счётчик лимита живут в памяти процесса. При нескольких репликах
  переносить в Redis.
